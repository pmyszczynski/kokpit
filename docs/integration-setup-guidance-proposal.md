# Integration setup guidance

Proposal and sequential delivery record, 23 October 2026. The owner accepted the Unraid design and authorized delivery of every integration, one at a time, including documentation research, full validation, PR/AI reviews, administrator merge and verified release before beginning the next integration.

## Editor design

Every integration gets a setup guide inside Add/Edit Service, beside the fields on desktop and above them on narrow screens. The guide stays visible as desktop users scroll through their settings. It follows the selected **integration**, including when that integration belongs to a plain link tile. Informational widgets with external providers get equivalent widget-specific guidance when implemented.

Each guide contains:

1. A short description of the data this connection supplies.
2. Prerequisites: supported service versions, API/plugin availability and authentication requirements.
3. Numbered steps with the exact upstream settings path, how to create/copy credentials, the permissions needed, where to paste them, and how to test and save.
4. Always-visible help under each field: purpose, example, default, units/range, and what leaving it empty does. Distinguish the API address from the optional tile launch URL.
5. An expandable troubleshooting section with specific symptoms and fixes.
6. An official documentation link that opens separately so the user's draft stays available.
7. A brief notice that instructions may become outdated, with a link to open a GitHub issue requesting a correction.

The form keeps its existing test, validation, saved-credential handling and YAML persistence. No setup step generates credentials or changes the upstream service. Keep instructions as typed registry metadata and reuse the presentation across integrations. Shared integration steps must be identical across a service's widgets; tile options retain their own help.

For all widgets, explain the refresh field in milliseconds and seconds, its actual default and 5-second minimum. Explain each footprint using the data it shows. Document optional credentials as optional; do not invent API keys for services that use passwords, sockets or public endpoints.

## First completed example: Unraid Stats

Implemented in `unraid-stats`, using a reusable `WidgetSetupGuide` and the existing field descriptions.

- Prerequisites distinguish the built-in API in Unraid 7.2+ from the Unraid Connect plugin on earlier versions. Local API access does not require a Connect account login.
- Four steps: open **Settings → Management Access → API Keys**; create a key named **Kokpit** with `READ_ANY` for `ARRAY` and `VARS`; copy it into API Key and enter the base URL; test and save.
- URL help explains protocol, optional port, automatic `/graphql`, and reachability from the Kokpit container.
- API Key help explains the data it authorizes, omitting the `Bearer` prefix, and retaining a saved key.
- Footprint help explains Compact (array/storage), Wide (also disk errors), and Detailed/Legacy (all six stats). Refresh help explains the 30-second default and 5-second minimum.
- Troubleshooting covers missing API settings, rejected/revoked credentials, container networking, trusted HTTPS certificates, and reverse-proxy/endpoint mistakes. The developer Sandbox is optional.
- Evidence: actual editor screenshots in `docs/assets/widget-ui/unraid-setup/`; browser coverage of desktop themes, mobile scrolling, keyboard disclosure, saved credentials and custom CSS.

Validation: type checking passed; lint passed with the existing unused `NetdataBaseConfig` warning. All 234 focused unit tests and 14 browser tests passed (setup guidance, settings UI and Unraid behavior). Browser checks used the environment's system Chromium. Screenshot inspection also caught and fixed the settings-input background shorthand resetting dropdown chevron placement/repetition.

Authoritative sources checked for the pilot:

- [Unraid API availability](https://docs.unraid.net/API/)
- [Using the API and managing keys](https://docs.unraid.net/API/how-to-use-the-api/)
- [Permission names and API key management](https://docs.unraid.net/API/programmatic-api-key-management/)

The widget's existing query requests `array` and `vars`; it performs no mutations. A live Unraid instance is still needed to verify the full upstream setup end to end.

### Sonarr documentation and implementation evidence

Checked 23 October 2026 against the [official Sonarr settings guide](https://wiki.servarr.com/sonarr/settings#general), [API documentation](https://sonarr.tv/docs/api/), and upstream [Security settings UI](https://github.com/Sonarr/Sonarr/blob/develop/frontend/src/Settings/General/SecuritySettings.tsx).

- **Getting the key:** General → Security contains the existing API Key and a copy button. The key grants application access. The guide tells users to copy it, explains the effect of resetting it, and does not invent a separate read-only key workflow.

The example Compose service is applied after configuring its secrets; shared Docker networks or reachable published addresses must cover both connection hops. The README example now uses the current 26.10.0 image, whose [package](https://github.com/jhonderson/actual-http-api/blob/26.10.0/package.json) declares `@actual-app/api` `^26.10.0`; the guide recommends compatible releases without asserting that every patch tag must match exactly.
- **Authentication and access:** the stable [key middleware](https://github.com/jhonderson/actual-http-api/blob/26.10.0/src/v1/middlewares/api-key-authorization.js) enforces `x-api-key` in production. The [budget router](https://github.com/jhonderson/actual-http-api/blob/26.10.0/src/v1/routes/index.js) accepts `budget-encryption-password` and optionally restricts `ALLOWED_BUDGET_SYNC_IDS`. The Actual login password remains in the bridge deployment; Kokpit uses the bridge API key, Sync ID and optional existing encryption password. Protect the bridge’s local budget cache as well as those secrets.
- **Sync ID, encryption and retention:** the official API example explicitly uses Settings → Show advanced settings → Sync ID and a separate download password for encrypted budgets. A local Budget ID is not the Sync ID. Actual’s sync guide confirms that reset-sync operations create a new ID; the widget instructions do not recommend resetting sync or enabling/changing encryption just to connect. Both saved secret fields are scoped to normalized bridge URL plus exact Sync ID; root trailing-slash equivalence and ignored fragments retain them, while normalized scheme/host/port/path/query or Sync ID changes require re-entry.
- **Transport and display settings:** checked Kokpit’s `actualFetch`, schemas, credential transport and formatters against the bridge’s [month](https://github.com/jhonderson/actual-http-api/blob/26.10.0/src/v1/routes/budget-months.js), [accounts](https://github.com/jhonderson/actual-http-api/blob/26.10.0/src/v1/routes/accounts.js) and [schedules](https://github.com/jhonderson/actual-http-api/blob/26.10.0/src/v1/routes/schedules.js) routes. Kokpit preserves real URL prefixes, appends `v1/budgets/{Sync ID}` and follows at most five same-origin GET redirects. Currency is explicit (default USD), and formatting does not convert amounts or auto-read budget preferences. Locale controls number formatting. Privacy blur is presentational and leaves values accessible. Timezone resolves Summary/Categories’ month and Schedules’ local day; invalid/blank names fall back to the server, normally UTC. Accounts intentionally has no timezone control. All widgets default to five-minute refreshes with the common five-second override minimum; they do not initiate bank sync.
- **Summary and Categories:** Summary’s size-default toggle shows 2/3/6 figures in Compact 3×2, Wide 6×2 and Detailed 3×4. New editor presets enable it; existing/YAML defaults retain all six, scrolling when necessary. Net Worth sums open accounts including off-budget balances and becomes — if the optional accounts request fails; Overspent counts non-hidden categories with negative balances. Categories uses one 3×4 footprint: hidden categories/groups are always excluded; income/untouched filters default on; untouched means both current-month budgeted and spent are zero even when carryover exists. It sorts by percent spent before applying a 1–50 limit (default 8). Available funds are balance plus absolute spending; negative balances take precedence over the 85% warning threshold.
- **Accounts and Schedules:** both use one scrolling 3×4 footprint. Accounts requests balances and retains the bridge’s returned order; closed accounts are excluded by default and off-budget accounts included. Both filters affect its footer total; they do not alter Summary’s separate calculation. There is no account-ID selector or item-limit control. Schedules keeps incomplete rows with a next date, including all returned overdue dates and future dates within a 1–365-day horizon (default 30), then sorts earliest first and displays up to 1–50 (default 6). Its footer counts the full filtered set due within `min(7, days_ahead)` days or overdue before limiting rows. Range amounts display their bounds; optional payee lookup falls back to the schedule name.

### Calendar documentation and implementation evidence

Checked 23 October 2026 against Nextcloud’s [calendar](https://docs.nextcloud.com/server/stable/user_manual/en/groupware/calendar.html), [device/app-password](https://docs.nextcloud.com/server/stable/user_manual/en/session_management.html) and [CalDAV-client authentication](https://docs.nextcloud.com/server/stable/user_manual/en/groupware/sync_android.html) guides, plus Google’s [public sharing](https://support.google.com/calendar/answer/37083), [Calendar ID lookup](https://support.google.com/calendar/answer/44105), [API enablement](https://developers.google.com/workspace/guides/enable-apis), [API-key credentials](https://developers.google.com/workspace/guides/create-credentials), [key management/restrictions](https://docs.cloud.google.com/docs/authentication/api-keys) and [events.list reference](https://developers.google.com/workspace/calendar/api/v3/reference/events/list). One guide explicitly marks the two alternative paths, including skipping credentials for an already anonymous CalDAV collection. Field descriptions explain values/conditions and refer to the canonical provider steps. The documentation link opens the Kokpit Calendar reference containing primary links for both providers.

- **Correct Nextcloud collection action:** checked tagged Calendar [6.6.3](https://github.com/nextcloud/calendar/tree/v6.6.3), whose [manifest](https://github.com/nextcloud/calendar/blob/v6.6.3/appinfo/info.xml) supports Nextcloud 32–35. For an owned calendar, [CalendarListItem](https://github.com/nextcloud/calendar/blob/v6.6.3/src/components/AppNavigation/CalendarList/CalendarListItem.vue) opens **Edit and share calendar**; [EditCalendarModal](https://github.com/nextcloud/calendar/blob/v6.6.3/src/components/AppNavigation/EditCalendarModal.vue) places **Internal link** in its sharing section; [InternalLink](https://github.com/nextcloud/calendar/blob/v6.6.3/src/components/AppNavigation/EditCalendarModal/InternalLink.vue) exposes **Copy internal link** and copies the calendar’s DAV collection URL. This differs from **Copy public link**, which copies an app sharing page, and **Copy subscription link**, which adds `?export`. Incoming shared/delegated calendars can hide the Internal link control, so the guide directs those users to their provider’s CalDAV client/discovery tools. Kokpit itself does not discover collections or accept ordinary ICS feeds.
- **Nextcloud credentials:** stable [Nextcloud 35’s token section](https://github.com/nextcloud/server/blob/stable35/apps/settings/src/components/AuthTokenSection.vue), [setup form](https://github.com/nextcloud/server/blob/stable35/apps/settings/src/components/AuthTokenSetup.vue) and [one-time dialog](https://github.com/nextcloud/server/blob/stable35/apps/settings/src/components/AuthTokenSetupDialog.vue) verify Devices & sessions → App name → Create new app password and the dialog’s Login/Password. The official manual confirms one-time visibility and the app-password requirement with 2FA. Known Kokpit credentials can be reused; the guide does not recommend disabling authentication or claim a read-only app-password scope.
- **Public Google path:** public sharing and **See all event details** are explicitly conditional on the user intending publication. **Settings and sharing → Integrate calendar → Calendar ID** supplies the email-like identifier; embed/share/iCal URLs and the authenticated `primary` alias do not fit Kokpit’s schema. Google Cloud → APIs & Services → Library enables Google Calendar API in the key’s project; Credentials → Create credentials → API key → Copy obtains the string. Dedicated keys avoid breaking unrelated clients when restricting APIs. API restrictions select Google Calendar API; application IP restrictions use Kokpit’s public egress, while website-referrer/mobile-app restrictions do not match server requests. A key identifies a project/quota and does not authorize private Google data or privatize a public calendar. OAuth/service-account login remains unsupported by this widget.
- **Schema, transport and saved secrets:** checked the explicit connection schema, fetcher and `credentialScope`. HTTP(S) Calendar values select CalDAV, with Basic username/password or both blank for an already anonymous REPORT collection; Google IDs require an API key and empty CalDAV fields. CalDAV usernames cannot contain a colon. Credentials use headers; Google calls a fixed HTTPS endpoint with `X-Goog-Api-Key`. Neither mode follows redirects. Real collection paths/proxy mounts and private/container addresses remain supported. The sole scope field is `calendar`, which is typed as text: saved password/key reuse requires the same Calendar text, without URL-normalization equivalence. Even a trailing-slash edit requires applicable secret re-entry. Username is outside the automatic scope, so account changes need the correct replacement password. Switching paths requires clearing unused saved secrets through Clear saved credential.
- **Options and dates:** Days ahead accepts 1–30/default 7 and is a rolling `now + N × 24h` window, with ongoing events included; it is not a midnight-based whole-date window. Event limit accepts 1–50/default 10, caps both footprints and the displayed header count. Time zone defaults to UTC and validates an IANA name instead of silently falling back. Timed display and local-day ordering use it; all-day dates retain their original calendar day and render the source’s exclusive end inclusively. Floating CalDAV timestamps use X-WR-TIMEZONE or the tile zone when absent. Current recurrence handling and unsupported RDATE-period/THISANDFUTURE errors are documented from the parser rather than guessed from provider capabilities.
- **Footprints and refresh:** Agenda 3×4 and Detailed 6×4 share the event window and limit. Events sort by local day, all-day first within a day and then timed starts; Detailed adds location, description and wrapped secondary text, without fetching more events. Empty results and stale recovery retain their existing behavior. Refresh defaults to five minutes, with the shared five-second override minimum and an existing fifteen-second fetch deadline. Large/complex CalDAV responses can hit bounded response/parser budgets; lowering the display limit alone does not shrink its REPORT query.
- The common outdated-instructions/GitHub-issue notice applies to both paths. Previews use isolated configuration and dummy credentials; live Nextcloud/Google connectivity has not been tested. Schemas, authentication, fetching, recurrence parsing, rendering, geometry and the shared guide component remain unchanged.
